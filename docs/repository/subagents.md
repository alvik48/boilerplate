# Subagents

A subagent is a delegated run with its own context window, its own system
prompt, and its own tool or sandbox restrictions. Definitions live under
`.agents/agents` and are generated into each tool's own directory.

## What A Subagent Is For

Two things, and neither of them is role specialisation:

- **Context economy.** Work that produces far more output than conclusion — the
  full gate run, a sweep across the docs tree — runs in a separate window and
  returns a summary. The caller's context stays available for the actual task.
- **Restricted authority.** A reviewer that cannot write is a stronger guarantee
  than a reviewer that has been asked not to.

Losing the conversation is the cost, and sometimes the point: an agent reviewing
a diff it did not write has no stake in the choices it is judging.

**Do not split subagents by role.** A "backend agent" and a "frontend agent"
duplicate what [skills.md](skills.md#core-skill-map) already routes by path,
minus the conversation. They also cut across the `project-feature-workflow`
skill, which is one procedure spanning both stacks, and neither half can run
`pnpm deps:check`, which decides dependency direction across the whole graph.

Domain expertise belongs in a skill, which loads into the current context.
A subagent is for work whose _output volume_ or _authority_ is the problem.

## Source Of Truth

`.agents/agents/<name>.md` — Markdown body plus YAML frontmatter, committed and
reviewed like any other repository content.

Unlike `.agents/skills`, this cannot be a symlink. Claude Code reads
`.claude/agents/<name>.md` (YAML frontmatter plus a Markdown body); Codex reads
`.codex/agents/<name>.toml` (flat TOML with the body as
`developer_instructions`). The formats are incompatible, so the neutral source is
generated rather than linked:

```sh
pnpm agents:generate-subagents
```

It runs from `prepare`, so `pnpm install` already does it. `.claude/` and
`.codex/` are gitignored, so output is rebuilt per clone rather than committed —
the same trade as [`agents:link-skills`](skills.md#discoverability).

**The trade a symlink does not have:** generated output goes stale. Editing a
file under `.agents/agents` does nothing until the generator re-runs. Re-run it
after every edit.

Generated files carry a `Generated by bin/agents.generate-subagents.mjs` marker on their
first line. The generator prunes only files carrying it, so a personal agent
placed in `.claude/agents` by hand survives. Do not hand-edit a marked file;
edit the source and regenerate.

## Source Format

Frontmatter is a deliberately small YAML subset: single-line `key: value`
scalars, plus one level of indentation under a bare `key:` for the per-target
tables. No arrays, no folded scalars, no anchors. The generator rejects anything
else with the offending line number rather than misparsing it.

```markdown
---
name: verify-runner
description: One line. Decides when the agent is selected, so lead with the trigger.
claude:
  model: sonnet
  tools: Bash, Read, Grep, Glob
codex:
  sandbox_mode: workspace-write
  model_reasoning_effort: medium
---

The body. Becomes the Markdown body for Claude Code and
`developer_instructions` for Codex.
```

`name` and `description` are required and shared. Every other key is namespaced
under `claude:` or `codex:` and passed through verbatim, because the two tools
diverge in substance rather than spelling:

| Concern         | Claude Code                | Codex                                       |
| --------------- | -------------------------- | ------------------------------------------- |
| Which tools     | `tools:` allowlist         | no equivalent — restrict via `sandbox_mode` |
| Write authority | omit `Edit`/`Write`/`Bash` | `sandbox_mode: read-only`                   |
| Model           | `model:`                   | `model:`, `model_reasoning_effort:`         |

Codex enforces `sandbox_mode` at the sandbox, so a read-only Codex subagent is a
real guarantee. Claude Code's `tools` list is enforced by the harness, but
granting `Bash` re-opens writing through the shell — a Claude Code subagent is
only genuinely read-only if it has no `Bash`.

`tools` takes **bare tool names only**. Scoped specifiers such as
`Bash(git diff:*)` are permission-rule syntax and do not work there; a subagent
needing that granularity needs a `PreToolUse` hook or a `permissions.deny` rule
instead. `diff-reviewer` accepts the looser form knowingly: it needs `git diff`,
so under Claude Code its read-only nature rests on its instructions, while the
same definition is sandbox-enforced under Codex.

A key the target does not recognise is passed through and ignored by it. The
generator validates structure, not the tools' own schemas.

## Body Rules

Link to repository documents; do not restate them. A subagent starts with a
fresh context and must open the document anyway, so pointing at the canonical
text is both shorter and drift-proof — the same rule the project-owned skills
follow. Restating a gate list in a subagent body creates a third copy that
silently diverges from [quality.md](quality.md).

State what **not** to do when the trap is invisible from the document alone.
`verify-runner` is told never to run a writing command, because `lint:fix` and
`format` both look like reasonable ways to satisfy a failing gate and both
invalidate the `git diff --exit-code` gate that follows.

## Current Subagents

| Agent           | Use when                                                                        |
| --------------- | ------------------------------------------------------------------------------- |
| `verify-runner` | Edits are finished and the Definition of Done gates need running and reporting. |
| `diff-reviewer` | The gates pass and the final diff needs review before committing.               |

Run them in that order. A reviewer reading a diff that does not compile spends
its findings on things the gates would have caught.

## Adding A Subagent

1. Write `.agents/agents/<name>.md`. Front-load the trigger in `description` —
   it is what decides whether the agent is ever selected.
2. Justify it against the two reasons above. If the answer is "it knows about
   NestJS", write or load a skill instead.
3. Run `pnpm agents:generate-subagents` and confirm both outputs.
4. Add it to the table above.

A subagent is repository content like a skill: adding one is a reviewed change,
not a command.
